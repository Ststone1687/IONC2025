講師：「我們這堂課要談的是如何降低常數，包括 I/O 優化。」
投影幕上顯示一行 cin >> x;。
講師：「很多人聽到 fast I/O 就會直接套 ios::sync_with_stdio(false); cin.tie(nullptr);，但你們知道這行到底幹了什麼嗎？」
朋友：「不是讓 cin 跑更快嗎？」
講師笑了笑：「是更快沒錯，但它其實是關閉了 cin 與 stdio 的同步。如果你再混用 scanf，就會因為兩套 buffer 打架導致讀取錯亂。」
妹妹：「……所以根本不能亂用？」
講師：「要看情況。如果整個程式只用 cin / cout，這樣做很好。但如果你 scanf / printf 混進來，就會出現預期外的問題。」
（原來我以前也沒意識到這些細節。）
講師在螢幕上打出了一段程式碼。
////////////////////
ios::sync_with_stdio(false);
cin.tie(nullptr);
int x;
scanf("%d", &x);
cout << x << "\n";
////////////////////
講師：「來，猜猜看這段程式會不會出問題？」
朋友皺眉：「不就是讀個數字再印出來嗎？應該沒事吧？」
講師：「錯。因為 ios::sync_with_stdio(false) 之後，cin 和 scanf 的緩衝區不再同步，導致輸入行為變得不可預測。某些情況下，你的 scanf 可能會讀到一個怪值，甚至被前面 cin 吃掉的輸入干擾。」
妹妹：「所以……其實有時候不開反而比較穩定？」
講師：「對。如果你必須混用 scanf 和 cin，保持同步是比較安全的。而若要速度，最好整段程式碼都選一派，不要混合。」
（這種細節，確實容易被忽略。）
講師繼續切換下一頁投影片。
講師：「有時候 cin 即使開了 sync_with_stdio(false)，速度還是比不上手刻 fread / fwrite。這就是更進一步的 I/O 優化，但程式碼可讀性會下降。」
學姊微笑著說：「感覺像為了爭一秒，寫出難以維護的程式……」
講師：「正是這樣，所以要依需求取捨。」
朋友：「不過，手刻 fread 感覺很酷欸！」
妹妹：「笨蛋，你連 cin 都常打錯字吧。」
朋友：「哎哎，不要戳我痛處啊！」
（看著他們的互動，我突然覺得，這堂課雖然難，但至少讓我理解了另一種層面的「細節即勝負」。）
講師：「I/O 只是常數優化的一環，接下來我們講更底層的一些技巧。」
投影幕切到一張圖，上面畫著 CPU 快取結構。
講師：「程式慢不一定是演算法的錯，有時候是記憶體取用的方式造成了快取未命中（cache miss）。
例如，我們先看這段雙層迴圈：」
////////////////////
int a[1000][1000];
for (int i = 0; i < 1000; i++)
    for (int j = 0; j < 1000; j++)
        a[j][i] = 0;
////////////////////
朋友：「咦？只是把陣列填零，有什麼問題嗎？」
講師：「問題很大。a[j][i] 這種存取方式是 column-major 走訪，但 C++ 陣列是 row-major 儲存。這樣會導致 CPU cache 幾乎無法預測下一個資料在哪裡，速度差距可能是數十倍。」
妹妹：「也就是說……要寫成 a[i][j] = 0; 才比較快？」
講師：「沒錯。對 cache 友善的寫法，能讓同樣的 O(n²) 跑得飛快。」
（我第一次意識到，這種看似無關的細節，會讓效率差距這麼誇張。）
講師：「還有一個技巧是利用 bitset 或 __builtin_popcount 等指令來降低常數。」
投影幕上出現一段篩法程式，先用普通陣列，再改成 bitset<1000000> 版本。
學姊輕聲說：「bitset 的好處是省記憶體、還能加速位元操作對吧？」
講師微笑：「正確，雖然有些人嫌它難用，但在某些題目裡速度提升非常明顯。」
朋友興奮地補充：「我知道！有時候 popcount 甚至比手寫 for-loop 快超多！」
妹妹挑眉：「你居然還知道這個？哼，難得不笨。」
（這對話聽起來像是小孩子在吵架……）
講師：「接下來，我們談談分支預測（branch prediction）。」
投影幕切換到一段程式碼：
////////////////////
for (int i = 0; i < n; i++) {
    if (a[i] % 2 == 0)
        even++;
    else
        odd++;
}
////////////////////
講師：「這段程式碼看似無害，但 CPU 的分支預測器會不斷猜測 if 的走向，錯誤就會導致 pipeline flush，增加常數。
如果你能把條件改寫成位元運算、或將常見的分支提早處理，就能微幅提速。」
朋友：「咦？只是改個 if 也能快？」
講師：「對，像是 odd += a[i] & 1; even += !(a[i] & 1); 就減少了預測失敗的風險。雖然看起來醜，但很有效。」
妹妹小聲吐槽：「看起來真的很醜……」
（我開始懷疑這種「為了速度犧牲可讀性」的做法是不是常態。）
講師：「另一個技巧是 unrolling loop。」
投影幕上出現兩段程式碼，一段是一般 for-loop，另一段展開成一次處理 4 筆資料。
講師：「這樣做可以減少迴圈控制的 overhead，尤其是對簡單運算，能快上幾十個百分點。」
學姊微笑著說：「但也要小心程式碼變得難維護。」
講師：「正確。常數優化的核心是取捨。」
講師：「最後，我們來談 SIMD 指令，例如 AVX2、SSE。」
他展示一段用 __m256i 同時處理 8 個 int 的範例。
朋友眼睛一亮：「這就是傳說中的同時加速！」
講師：「沒錯，但它需要你熟悉硬體特性，對初學者而言難度高。」
妹妹：「我才不要碰那種怪東西……」
講師笑道：「沒關係，今天只是讓你們知道它的存在。」
講師收起簡報，總結道：
「常數優化就像最後的調味料，單獨看不起眼，但往往決定能不能 AC。細節、記憶體取向、I/O、甚至 CPU 架構，都值得深入研究。」
（我默默寫下筆記，感覺腦子快被這堂課塞滿了。）
